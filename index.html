Case Study: Advantage Health Africa

How I engineered a high-performance vendor analytics backend for pharmacy Point-of-Sale (POS) and supplier management.

Healthcare Technology • Backend Engineering

Pharmacy Vendor Partnership Statistics API

Designing a single-roundtrip, multi-tenant analytics endpoint in NestJS, TypeORM, and PostgreSQL to give community pharmacies real-time operational visibility into their supplier network.

Organization
Advantage Health Africa
My Role Backend Developer Intern
Domain Pharmacy Operations & POS Systems
Core Technologies NestJS · TypeScript · PostgreSQL · TypeORM
API Standards RESTful · Swagger/OpenAPI · Postman

1. The Real-World Problem

Advantage Health Africa develops healthcare platforms including a pharmacy Point-of-Sale (POS) system. In daily operations, pharmacists use the POS to search and select drugs, calculate pricing, and print receipts for customers.

Beyond frontline counter dispensing, pharmacies depend on multiple pharmaceutical distributors to replenish inventory. However, pharmacies lacked a unified way to monitor their supplier relationships:

  • No visibility into total registered vendor partnerships.
  • Inability to separate active suppliers from inactive/lapsed contracts.
  • Multiple disjointed database queries risked high latency and data inconsistency.

2. The Backend Solution

I engineered the dedicated backend endpoint within Advantage Health Africa's modular NestJS architecture:

GET /v1/vendors/rx/{pharmacyId}/partnerships/stats

Key architectural decisions implemented:

  • Multi-Tenant Isolation: Validates pharmacyId to guarantee strict tenant isolation.
  • Controller-Service Separation: Kept HTTP validation cleanly isolated from database query execution.
  • Consolidated Payload: Returns total vendors, active partnerships, and inactive partnerships in one roundtrip.

3. Engineering Concepts

Core software engineering and database principles applied throughout development:

  • Relational Modeling: Configured TypeORM entities mapping Many-to-Many / One-to-Many partnerships between pharmacies and vendors.
  • Query Optimization: Minimized database I/O using conditional counts grouped by partnership status.
  • Swagger / OpenAPI: Documented endpoint schemas, route parameters, and response contracts for frontend parity.
  • Postman Test Suites: Automated verification of 200 OK statuses, error handling, and parameter guards.
System Architecture & Request Lifecycle
NestJS • TypeORM • PostgreSQL
Step 01 • Client Pharmacy POS / Web App Pharmacy requests supplier statistics using its unique pharmacyId identifier.
Step 02 • Gateway API Request Routing GET /v1/vendors/rx/{pharmacyId}/partnerships/stats with Bearer Auth.
Step 03 • Controller NestJS VendorsController Extracts parameters, enforces route validation, and delegates to the service layer.
Step 04 • Service VendorsService & TypeORM Executes optimized aggregation queries scoped strictly to the pharmacy record.
Step 05 • Database PostgreSQL Database Queries vendor partnerships table; calculates total, active, and inactive counts.
Step 06 • Response Consolidated JSON Returns structured 200 OK payload containing totalVendors, active, and inactive metrics.
